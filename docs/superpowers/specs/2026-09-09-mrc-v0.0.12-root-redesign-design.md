# MRC v0.0.12 Root Redesign — Design Specification

**Date:** 2026-09-09  
**Owner:** Doonchy  
**Repository:** `doonchy16-cloud/MRC`  
**Branch:** `redesign-v0.0.12`  
**Baseline:** `precert-v0.0.11`  
**Final certification target:** `v0.1.0`

## 1. Goal

Rebuild MRC at root level so that runtime ownership, diagnostics, repair, CLI presentation, release-stage handling, single-instance behavior, GUI presentation, animation, application identity, and verification form one coherent architecture while preserving all proven safety and update guarantees.

V0.0.12 is a pre-certification redesign build, not final v0.1.0 certification.

## 2. Non-Negotiable Safety Constraints

MRC remains authorized only on Windows machine `DOONCHYSCOMPUTI` and only for managed runner folders immediately beneath `D:\Git_Runners_Main`.

MRC must never:

- control runner processes whose ownership is external or unattributed;
- register/unregister GitHub runners;
- edit runner credentials;
- manage GitHub runners as Windows services;
- require Administrator rights by default;
- normal-stop a BUSY runner;
- include BUSY runners in TURN ALL OFF;
- stop runners merely because the MRC GUI closes;
- weaken SHA-256/package/activation/rollback verification.

## 3. Root Architecture

### 3.1 Runtime domain

Introduce explicit runtime concepts:

- `ManagedRunner` — a configured runner discovered beneath the authorized root;
- `ObservedRunnerProcess` — an observed `Runner.Listener`, `Runner.Worker`, or runner service process;
- `ProcessOwnershipClass` — `Managed`, `External`, `Unattributed`;
- `RunnerProcessAssociation` — exact association between a managed runner and its proven listener/worker tree;
- `ExternalRunnerObservation` — runner-related process proven outside the managed root;
- `UnattributedRunnerObservation` — runner-related process whose exact path/ownership cannot be proven;
- `RuntimeSnapshot` — one immutable observation cycle containing managed runner states plus external/unattributed warnings.

Global inventory uncertainty must never automatically contaminate every managed row. Uncertainty affects only the runner whose ownership could materially overlap that uncertainty.

### 3.2 Diagnostics domain

Split diagnostics into two products:

- **Diagnose** — read-only, deep forensic reporting;
- **Doctor** — find, optionally repair, verify, and grade health.

Doctor repairs are classified by safety tier:

- `AutoRepair` — low-risk MRC-owned state only;
- `ApprovalRequired` — destructive, runner-affecting, service-affecting, or process-affecting operations;
- `Blocked` — outside MRC authority.

### 3.3 CLI presentation domain

Create one semantic renderer used by every CLI command. Rendering is semantic rather than command-specific. Commands emit structured output records; the renderer decides color/plain-text representation.

### 3.4 GUI domain

Recompose the GUI around a terminal-style operations shell rather than dashboard cards. The runner table is the primary surface. System/external warnings are separate from runner state rows.

### 3.5 Release/update domain

Represent semantic version, release channel, release stage, and final target separately. Pre-certification builds must be updateable without pretending they are final releases.

### 3.6 Instance coordination

Introduce a single-instance coordinator. A second `MRC` invocation signals the existing GUI to restore/focus itself and reports the result in PowerShell.

## 5. Folder Classification

Immediate child directories under `D:\Git_Runners_Main` are classified into:

1. `ManagedRunner` — full configured runner signature;
2. `BrokenRunnerCandidate` — meaningful runner artifacts exist but configured signature is incomplete/contradictory;
3. `NonRunnerFolder` — no meaningful runner signature evidence.

Known non-runner folders from live testing:

- `dash-echo`
- `Forgey_Trainer`
- `HardwareMonitor`
- `RA-OS`
- `Subagents_runner`

These folders must not cause Doctor failure solely because they are beneath the root.

## 6. Runtime State Derivation

The six canonical user-visible managed-runner states remain:

- OFF
- STARTING
- IDLE
- BUSY
- STOPPING
- ERROR

Baseline derivation:

- listener absent and no active transition -> OFF;
- listener present and no worker -> IDLE;
- listener present and worker present -> BUSY;
- launch transition pending -> STARTING;
- stop transition pending -> STOPPING;
- managed-runner-specific ownership/state evidence contradictory or unavailable -> ERROR.

External/unattributed process warnings are not additional runner states.

## 7. Diagnose Command

Canonical forms:

- `MRC -diagnose`
- `MRC --diagnose`

Optional targeted syntax:

- `MRC -diagnose <runner-name>`
- `MRC --diagnose <runner-name>`

Diagnose is read-only and reports, as applicable:

- machine identity;
- authorization fence result;
- process elevation state;
- runner root;
- installed MRC version/channel/stage/target;
- managed runner discovery;
- folder classification;
- listener/worker PID;
- parent PID;
- session ID;
- executable path;
- process inspection method;
- raw Win32 inspection errors;
- expected canonical runner paths;
- ownership proof result;
- managed/external/unattributed classification;
- Windows service identity when present;
- runtime state derivation;
- update/install/rollback metadata;
- PATH state;
- release source reachability.

## 8. Doctor Command

Canonical forms remain:

- `MRC -doctor`
- `MRC --doctor`

Workflow:

1. FIND — execute health checks;
2. CLASSIFY — pass/warn/fail plus repairability;
3. REPAIR — auto-repair low-risk MRC-owned issues and request explicit approval for higher-risk eligible repairs;
4. VERIFY — rerun affected checks;
5. RESULT — report exactly one final grade.

Final grades:

- HEALTHY — no material finding;
- REPAIRED — one or more findings were successfully repaired and reverified;
- ATTENTION — non-blocking findings remain or explicit approval is required;
- BLOCKED — safety/authority prevents healthy operation.

Doctor must never claim repair merely because a repair action executed.

## 9. Doctor Repair Authority

Examples of eligible automatic MRC-owned repairs:

- missing/stale MRC user PATH entry;
- duplicate MRC user PATH entries;
- broken MRC active-version pointer/launcher state;
- stale MRC-owned temporary update state;
- recoverable MRC install metadata;
- broken MRC-owned shortcut/icon registration where installer metadata is sufficient;
- recoverable rollback metadata where immutable version payloads remain valid.

Examples requiring explicit approval:

- process termination;
- service modification/removal;
- deletion of runner-related files/folders;
- runner configuration change;
- anything that could interrupt an active runner/job.

Operations outside MRC scope are reported but not offered as repairs.

## 10. CLI Semantic Rendering

Color semantics:

- green: PASS, success, verified, healthy;
- red: FAIL, error, blocked;
- yellow: warning, attention, skipped, rollback retained;
- cyan: headings, actions, paths, operational metadata;
- purple: versions, release/build metadata;
- gray: secondary technical text.

Color must never be the only state signal.

When output is redirected, piped, or color support is unavailable, output remains complete and readable without ANSI/control-noise.

## 11. Bare MRC Launch Behavior

First invocation:

- print launch acknowledgement;
- launch GUI without holding PowerShell open unnecessarily.

If GUI already exists:

- detect existing instance;
- signal it to restore/focus;
- print `already running` plus focus/restore result;
- do not silently launch-and-exit a duplicate GUI.

## 12. Update Presentation and Release Semantics

Update output uses visible stages:

- resolve release;
- compare current/available version;
- download;
- SHA-256 verification;
- package/manifest verification;
- extract/install;
- atomic activation;
- launchability verification;
- rollback retention;
- final result.

Release metadata distinguishes:

- `Version` — e.g. `0.0.12`;
- `Channel` — e.g. stable-compatible update policy;
- `Stage` — e.g. `pre-certification`;
- `FinalTarget` — `0.1.0`.

Doctor and Version must not falsely report an Owner-authorized 0.0.x pre-cert build as invalid.

The update source must support allowed pre-cert builds directly rather than requiring them to masquerade as final/stable GitHub `latest` releases.

Atomic-update and rollback guarantees remain unchanged.

## 13. Terminal GUI Design

### 13.1 Shell

Target character: native Windows PowerShell/terminal operations console.

Default target remains approximately 1180x760; minimum approximately 900x560.

Use:

- near-black background;
- Cascadia Mono when installed, with Consolas fallback;
- compact title/identity header;
- inline authorization badge;
- one-line compact counters;
- compact operation/filter/search strip;
- table-first layout;
- flat separators instead of oversized cards;
- low-padding controls;
- dedicated external/system warnings area;
- compact terminal-style bottom status feed.

### 13.2 Main runner table

Canonical columns remain:

- STATUS
- RUNNER NAME
- REPOSITORY
- STATE
- CONTROL

Table is the dominant visual surface and expands to consume available vertical space.

Rows remain single-line and stable-sorted. Long names ellipsize.

### 13.3 Diagnostics UI

Replace generic Windows message boxes for runner diagnostics with a native MRC-styled details surface containing:

- runner identity;
- state;
- process evidence;
- ownership result;
- exact error;
- safety explanation;
- diagnostic next action when applicable.

### 13.4 Accessibility

All semantic state remains available through text/icon/shape in addition to color. Keyboard navigation and focus visibility remain required.

## 14. Animation

The state glyph language remains:

`/ - \\ |`

State behavior:

- OFF: frozen `-`, red;
- IDLE: slow green spin;
- BUSY: fast yellow spin;
- STARTING: medium-fast blue spin;
- STOPPING: medium purple spin;
- ERROR: frozen `!`, orange.

One shared animation clock is mandatory. No timer per row.

Presentation may add subtle intensity/pulse treatment driven by the same shared clock when it improves readability without misleading state.

## 15. Application Icon

Create one MRC icon family derived from a near-black terminal tile with cyan prompt/identity and green runner/activity accent.

Integrate it into:

- CLI/GUI executable resources as appropriate;
- GUI window/title bar;
- taskbar;
- Alt-Tab;
- installed shortcuts;
- packaging/install metadata.

The icon must remain legible at common Windows small-icon sizes.

## 18. Certification Rule

Implementation completeness and certification are separate gates.

V0.0.12 may be called implementation-complete only when every RR-001 through RR-090 has implementation and verification evidence.

It may be called PASS only when every applicable review category is exactly 10.0/10 and there are no unresolved or unverified requirements.
