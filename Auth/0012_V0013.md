## 2. Owner-Observed V0.0.12 Issue
Live Main-PC `MRC --version` output in v0.0.12 uses line-level semantic coloring, causing labels such as `Version:`, `Channel:`, `Stage:`, `Final target:`, `Install location:`, and `Runner root:` to inherit the value color.

The Owner explicitly requires for v0.0.13:

> labels: white; others: their deserving color.

## 3. Locked V0.0.13 Rule
CLI output SHALL support segmented/token-level semantic rendering within one logical line.

Human-readable field labels SHALL render white.

The associated dynamic value/result/status token SHALL render in its semantically appropriate color.

Examples:

- `Version:` = white; `0.0.13` = purple/version color.
- `Channel:` = white; `precert` = purple/metadata color.
- `Stage:` = white; `PRE-CERTIFICATION` = purple/metadata color.
- `Final target:` = white; `0.1.0` = purple/version color.
- `Install location:` = white; filesystem path = cyan/path color.
- `Runner root:` = white; filesystem path = cyan/path color.
- `PASS` / successful result value = green.
- warning/attention result value = yellow.
- FAIL/blocked/error result value = red.
- secondary technical value = gray when appropriate.
- ordinary unclassified prose = white.

Headings/product identity may retain their deserving semantic accent color where they are not field labels. This amendment specifically forbids coloring an entire label/value line as one semantic block when the label and value have different semantic roles.

## 4. Renderer Requirement
The CLI renderer SHALL support multiple semantic spans/tokens on a single line rather than only one tone per complete line.

The implementation should preserve one central semantic rendering authority rather than creating command-specific manual color calls.

Redirected/non-interactive output MUST remain deterministic plain text with no ANSI escape sequences or other color-control garbage.

## 5. Scope
Apply the segmented label/value rule consistently wherever a CLI line contains a human-readable label followed by a semantic value, including at minimum:

- `MRC --version` / aliases;
- `MRC -doctor` / `--doctor`;
- `MRC -diagnose` / `--diagnose`;
- `MRC -update` / `--update` where stage/result lines have distinct labels and values;
- `MRC --help` where semantic highlighting is useful without reducing readability.

Do not recolor labels merely to maximize visual variety. White labels are the stable reading scaffold; values carry meaning through semantic color.

## 9. Owner Scope Expansion — Global Control Root Repair
**Owner correction:** 2026-09-09/10 Pacific.

The Owner explicitly clarified that the observed OFF/ERROR and restart/session-conflict behavior is not a `TURN ALL OFF` defect. It is a defect in the shared global control lifecycle and must be repaired at the common control/runtime authority used by individual and bulk operations.

### 9.1 Managed-State Truth
Unrelated unresolved runner processes SHALL NOT contaminate the state of a managed runner unless they can be positively associated with that managed runner.

Managed runner state is derived from exact per-runner evidence. Separate external/unattributed system evidence remains visible as system evidence rather than being projected onto unrelated managed rows.

### 9.2 Control Safety
The state/display repair SHALL NOT weaken mutation safety. Start/stop mutation paths must remain fail-closed where target ownership is genuinely uncertain.

A proven external/system runner is non-controllable and must not be mistaken for a managed runner merely because its executable path is unavailable to the current user.

### 9.3 Normal Stop Lifecycle
Normal stop of an IDLE managed runner SHALL use graceful GitHub-runner-compatible Windows shutdown first when safe and available, then bounded fallback termination only if graceful shutdown fails or times out.

A stop request is not equivalent to a stopped runner. MRC SHALL verify the exact managed listener/worker processes have exited before reporting the control operation as completed `OFF`.

Hard process-tree kill remains a fallback only after fresh exact ownership/BUSY revalidation.

### 9.4 Restart Safety
A subsequent start SHALL NOT race an incomplete stop. Immediate restart is allowed only after the prior managed runner lifecycle is reconciled to verified `OFF`.

### 9.5 Shared Ownership Evidence
Windows `actions.runner.*` service evidence used by Diagnose SHALL be brought into shared runtime/control ownership classification so external service-hosted runners can be positively identified as external/system evidence without poisoning managed rows or weakening start safety.
