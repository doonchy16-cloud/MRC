## 1. Governing Repair Rule
V0.0.13 is no longer limited to CLI presentation work. The Owner explicitly authorizes root-core repairs for defects discovered during live Main-PC acceptance.

Symptom patches, UI suppression, hard-coded per-runner exceptions, and special-case masking are forbidden. Each defect must be repaired at the subsystem that owns the incorrect truth or behavior, with regression coverage and real Main-PC verification.

The previously stated expectation of seven IDLE runners is superseded.

## 3. P0 Global Control-Lifecycle Correctness
The Owner observed that control operations can close the visible runner PowerShell windows while MRC changes affected managed runners to ERROR rather than OFF, and a later restart can encounter a runner duplication conflict.

This is a global control-system defect, not a `TURN ALL OFF`-specific defect. The root repair must cover the shared lifecycle used by individual and bulk start/stop paths.

Required invariants:

- An unrelated unresolved or inaccessible runner process must not contaminate the state of a managed runner unless evidence can positively associate that process with that managed runner.
- A managed runner with no positively associated listener and no same-runner contradictory evidence is OFF.
- External/unattributed runner evidence remains visible in the dedicated system findings surface and remains non-controllable.
- Stop success must not be confused with mere termination request acceptance. Control lifecycle must reconcile toward actual process exit and truthful OFF state.
- Start must remain blocked whenever the target managed runner has a positively associated existing listener or other same-runner contradictory evidence.
- BUSY protection, exact-path ownership, force-stop confirmation, machine/root fences, and external-runner non-control remain mandatory.
- Individual and bulk controls must use the same authoritative lifecycle semantics.

## 4. P0 External / Unattributed Isolation
Current source behavior that lets one globally unresolved `Runner.Listener` or `Runner.Worker` make every otherwise-OFF managed runner ERROR violates the exact per-runner association principle and must be removed at the association/ownership core.

An inaccessible runner process may remain UNATTRIBUTED when exact ownership cannot be proven. That uncertainty must not be silently promoted to managed ownership and must not be globally projected onto unrelated managed rows.

## 5. CLI Semantic Renderer + Help
The `Auth/0012_V0013.md` segmented CLI authority remains in force.

Additionally:

- Help output shall use a readable semantic hierarchy rather than a flat all-white wall.
- Canonical commands are visually primary; aliases are visually secondary.
- Help command/description alignment must be consistent and avoid unnecessary one-off wrapping at ordinary terminal widths.
- Redirected output remains deterministic plain text.

## 6. Read-Only Update Check
Add canonical `MRC --check` with case-insensitive parsing consistent with the existing CLI.

`--check` is read-only. It may resolve and compare the newest authorized release but must not download, install, activate, mutate rollback state, or weaken release/channel authority.

Semantic status colors:

- UP TO DATE = green
- UPDATE AVAILABLE = cyan/informational, not yellow
- metadata/version values = purple
- labels = white
- warning/attention = yellow only for genuine caution
- failure/blocked/invalid = red

## 7. GUI Readability and Composition
The live 2048×1222 screenshot shows the application materially underscaled at normal viewing size.

V0.0.13 must improve readability at the owning GUI style/layout layer while preserving the 900×560 minimum-size requirement and terminal-console identity.

Required outcomes include larger readable typography, controls, row/state glyphs, table headers, system-finding strip, and footer telemetry; clearer search-shortcut presentation; stronger runner-table hierarchy; and responsive use of available canvas without giant dead-space composition or bloated card UI.

The native title-bar/accent behavior must be reviewed deliberately so OS chrome does not accidentally overwhelm MRC semantic colors. Do not override user/OS preference without a justified product-level reason.

## 8. Animation Timing
The Owner requires the shared animation engine to run at a true 20 Hz / 20 FPS clock target: 50 ms per shared UI tick.

Per-state motion personality may retain state-specific frame progression, but the shared engine cadence itself must be 50 ms. Animation remains presentation-only and must never determine runtime truth.

## 9. Diagnostics Presentation
Duplicate diagnostic text such as repeated identical `Access is denied.` fragments must be deduplicated when they represent the same surfaced message, without discarding distinct evidence from separate inspection dimensions.
