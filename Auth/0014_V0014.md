## 2. P0 — Global Control Action Reliability
The Owner reported that clicking an enabled runner control could return an error instead of starting the runner. The live v0.0.13 GUI simultaneously showed an unrelated Session-0 `Runner.Listener` as UNATTRIBUTED with inaccessible path/parent evidence. Current START preflight is allowed to fail closed for genuinely unattributed runner processes, but unrelated external/system runners must not create a permanent global blocker when ownership can be proven safely.

### 2.1 Root-cause doctrine
- Do not patch a button or suppress the error in the GUI.
- Do not weaken fail-closed mutation safety.
- Improve the shared Windows ownership evidence so protected/inaccessible runner processes can be correlated to external `actions.runner.*` services when proof exists.
- Prefer process-enumeration evidence that does not require opening the protected process merely to learn its parent PID.
- A genuinely unattributed runner process remains visible and continues to block unsafe START mutation.
- A proven external/system runner remains visible, non-controllable, and must not block unrelated managed runner starts.

### 2.2 Shared lifecycle contract
Every enabled GUI control and every bulk control SHALL use the same verified core lifecycle:
- START: validated managed runner + verified OFF + safe ownership preflight -> launch through that runner folder's `run.cmd` -> STARTING -> observed IDLE/BUSY.
- STOP: verified IDLE -> graceful GitHub-runner-compatible shutdown -> exact exit verification -> bounded hard-kill fallback only if needed -> verified OFF.
- RESTART: verified IDLE -> complete verified STOP to OFF -> safe START -> STARTING -> observed IDLE/BUSY. No fixed-delay kill/start shortcut.
- BUSY: normal STOP and RESTART remain protected. Force stop remains a separate confirmed path.
- ALL ON: targets only verified OFF managed runners through the same START core.
- ALL OFF: targets only verified IDLE managed runners through the same STOP core and never force-stops BUSY runners.
- ERROR: exposes diagnostics; unsafe mutation is not enabled merely to make the button clickable.
- EXTERNAL / UNATTRIBUTED: no control path.

### 2.3 Control acceptance
Automated tests must prove:
- unrelated proven external service runner does not block managed START;
- genuinely unattributed inaccessible runner still blocks managed START;
- restart waits for verified OFF before start;
- restart cannot operate on BUSY without the existing protection path;
- individual and bulk controls delegate to the same shared lifecycle methods;
- repeated OFF -> START -> IDLE -> STOP -> OFF -> START does not create a duplicate-session race in the modeled lifecycle.

Live Main-PC acceptance must repeat START/STOP/RESTART and bulk operations, not only perform each once.

## 3. T01 — Bare `MRC` Launch Experience
The bare `MRC` command is a first-class terminal command and SHALL use the central semantic CLI presentation/renderer pipeline.

The v0.0.13 direct `TextWriter.WriteLineAsync` launch output is superseded.

Requirements:
- multi-line MRC-branded launch result, not a single generic sentence;
- semantic segmented colors in interactive PowerShell/Terminal;
- deterministic plain text when redirected;
- cyan product/command heading;
- white field labels;
- green success/result token for successful launch/activation;
- metadata/secondary detail uses the existing semantic palette;
- distinguish `OPENED` from `ALREADY RUNNING` / restored-and-focused behavior truthfully;
- failed launch remains a non-zero exit and uses the central error renderer;
- no fake progress bar or fabricated launch stages;
- no command-specific `Console.ForegroundColor` calls.

The output should feel like an MRC control-console event while remaining concise.

## 4. T02 — Help as a Real Terminal Table
`MRC --help` SHALL render as a scan-friendly terminal command-reference table rather than command rows followed by alias footnotes.

Requirements:
- one command record per logical row;
- explicit `COMMAND`, `ALIASES`, and `DESCRIPTION` column headers;
- canonical command in cyan;
- aliases in gray/secondary tone;
- description in white;
- stable column alignment;
- long descriptions wrap only within the DESCRIPTION column and continuation lines align under DESCRIPTION;
- preserve every supported alias;
- redirected output remains deterministic plain text;
- ordinary terminal widths remain readable without orphaned command/description lines;
- no box-heavy generic spreadsheet/card styling; preserve MRC terminal aesthetic;
- central reusable table/column formatting rather than ad hoc spaces per command.

## 5. T03 — Update Progress Bar
`MRC --update` SHALL add a truthful terminal progress bar driven only by existing `UpdateProgress.Percent` authority.

Requirements:
- no fake time-based or animated percentage;
- central reusable progress-bar formatter;
- bounded width safe for ordinary terminals;
- semantic stage/result coloring preserved;
- redirected output deterministic plain text with no ANSI/control garbage;
- 100% only when updater reports 100%;
- progress-bar presentation must not alter updater execution, verification, activation, rollback, or release selection behavior.

## 6. T04 — Native Command Center GUI
The Owner selected a Hybrid C+ direction: MRC remains a native Windows application, but the GUI SHALL become a modern purpose-built control center instead of a fake terminal table.

### 6.1 Visual reference doctrine
The supplied Runner Control screenshot is a visual reference only, not a pixel copy. Adopt its useful traits:
- clear separation between runner surfaces;
- large runner identity;
- obvious state badge/indicator;
- real START / STOP / RESTART controls;
- strong app hierarchy and spacing;
- dark technical control-room feel;
- clear enabled/disabled states.

Preserve MRC identity rather than copying another product's colors, naming, layout, or exact styling.

### 6.2 Hybrid visual language
Use polished application UI for:
- header / authorization / health;
- counters and state summaries;
- search and filters;
- runner cards;
- bulk controls;
- system findings summary;
- primary interaction.

Retain terminal/monospace DNA selectively for:
- paths;
- PIDs / sessions;
- CLI commands;
- diagnostic detail;
- build/version metadata;
- event/log style text.

The full GUI must not look like a fake terminal and must not regress into a generic consumer dashboard.

### 6.3 Responsive runner-card layout
- default 1200x760 and minimum 900x560 remain supported;
- large-screen 2048x1222 remains an acceptance viewport;
- card layout adapts by available width instead of globally scaling one rigid table;
- target approximately 3 generous columns on very large screens, 2 columns around the default canvas, and a readable minimum layout at 900 width;
- all managed runners remain discoverable; scrolling is allowed when needed at narrow/minimum sizes;
- no giant empty black ocean around tiny controls.

### 6.4 Runner card interaction
Each managed runner card must expose:
- state indicator/badge;
- runner name;
- repository name;
- START;
- STOP;
- RESTART;
- diagnostic/details affordance when relevant.

Enabled state must reflect what the shared core can safely perform:
- OFF: START enabled; STOP/RESTART disabled;
- IDLE: STOP and RESTART enabled; START disabled;
- BUSY: ordinary STOP/RESTART protected; no silent force action;
- STARTING/STOPPING: controls disabled while transition is in progress;
- ERROR: diagnostic/details path, not unsafe start/stop guessing.

Buttons are functional controls, not decoration. A visually enabled button that cannot reach the corresponding authorized core operation is a defect.

### 6.5 System findings
External/unattributed evidence remains visually separate from managed runner cards. External/system processes must never receive managed controls. Diagnostic details remain available without allowing global system findings to contaminate unrelated managed card state.
