# MRC V0.1 — CLI & Distribution Authority

## Canonical Command
There is one primary PATH command:

`MRC`

No separate canonical executables such as `MRC-version` or `MRC-update`.

## Supported Flags
### GUI
`MRC`
- launches the control center;
- does not hold the invoking PowerShell session open unnecessarily;
- should prevent accidental duplicate GUI instances.

### Version
All equivalent:
- `MRC -v`
- `MRC -version`
- `MRC --version`

Expected information:
- product name;
- installed version;
- release channel;
- install location;
- runner root.

### Update
Equivalent:
- `MRC -update`
- `MRC --update`

### Doctor
Equivalent:
- `MRC -doctor`
- `MRC --doctor`

Doctor should validate at minimum:
- machine identity;
- runner root existence;
- PATH installation;
- version authority;
- discovered runner count;
- runner signature completeness;
- update endpoint/release reachability when applicable.

### Help
All equivalent:
- `MRC -h`
- `MRC -help`
- `MRC --help`

## PATH Installation
Use a user-scoped installation model. Avoid Administrator requirement by default.

Recommended conceptual layout:

`%LOCALAPPDATA%\MRC\`
- `bin\` — PATH-visible command launcher;
- `versions\<version>\` — immutable installed version payloads;
- `current\` — active-version pointer/indirection;
- `config\` — small local configuration if needed.

Only `%LOCALAPPDATA%\MRC\bin` should need to be added to the user PATH.

## Release Naming
Use SemVer tags and release assets:
- `v0.1.0`
- `MRC-v0.1.0-win-x64.zip`
- `SHA256SUMS.txt`

## Update Atomicity
Updates must not overwrite the current working version file-by-file.

Preferred sequence:
1. resolve latest release;
2. download candidate;
3. verify SHA-256;
4. extract to a new version directory;
5. validate required files;
6. switch active version atomically;
7. verify launchability;
8. retain previous version for rollback.

If validation fails, remain on the previous working version.
